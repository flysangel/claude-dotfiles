# Feature Specification: 公開 repo 入庫防護

**Feature Branch**: `001-repo-commit-guard`

**Created**: 2026-11-05

**Status**: Draft

**Input**: User description: "建立 claude-dotfiles 公開 repo 的入庫防護基礎：用白名單定義哪些個人化 Claude Code 設定可以納管進 repo，其餘一律排除；在 commit 前自動掃描待提交內容，發現憑證、token、email、個人路徑等機密或個資時阻止提交。使用者會在 Windows 與 Linux 上開發。也要有方式檢視現有的 ~/.claude/settings.json，判斷哪些內容可以共用、哪些含機密或屬於機器專屬，不能入庫。這是 repo 公開前必須完成的第一個功能。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Commit 時自動攔下機密與個資 (Priority: P1)

維護者在 Windows 或 Linux 上提交變更時，防護會自動檢查這次要提交的內容與作者資訊。只要發現憑證、token、email 或個人路徑，就阻止提交，並指出位置與類型，讓維護者能修正後再提交。

**Why this priority**: 內容一旦進入公開的 git 歷史就無法真正收回，這是憲章原則 I 最直接的防線，也是公開 repo 的前提。

**Independent Test**: 在測試 repo 暫存含假憑證、假 email、假個人路徑的檔案後嘗試提交，確認每一種都被阻止；再提交乾淨內容，確認能順利完成。

**Acceptance Scenarios**:

1. **Given** 待提交內容含 token 格式的字串，**When** 維護者提交，**Then** 提交被阻止，訊息列出檔案、行號與類型，且不顯示該 token 的完整值。
2. **Given** 待提交內容含其他人或自己的 email，**When** 維護者提交，**Then** 提交被阻止。
3. **Given** 待提交內容含 Windows 或 Linux 的個人家目錄絕對路徑，**When** 維護者提交，**Then** 提交被阻止。
4. **Given** 工作區檔案已清理但暫存區仍是舊內容，**When** 維護者提交，**Then** 依暫存區內容判斷並阻止提交。
5. **Given** 提交的作者或提交者 email 不是公開安全的地址，**When** 維護者提交，**Then** 提交被阻止，並提示如何改用不公開個人信箱的地址。
6. **Given** 待提交內容沒有任何違規，**When** 維護者提交，**Then** 提交正常完成，不需要額外操作。

---

### User Story 2 - 只有白名單內的檔案能入庫 (Priority: P1)

維護者用一份白名單明確列出可納管的路徑。任何不在白名單內的檔案都不能提交，即使被明確加入暫存區也一樣，確保 `~/.claude/` 裡的憑證檔、對話紀錄這類檔案不會意外進入 repo。

**Why this priority**: 內容掃描無法辨識所有機密，白名單從範圍上先排除風險，兩者互補，憲章原則 I 也明確要求。

**Independent Test**: 暫存一個白名單外的檔案並嘗試提交，確認被阻止；將該路徑加入白名單後再提交，確認通過內容掃描後可完成。

**Acceptance Scenarios**:

1. **Given** 暫存了白名單外的檔案，**When** 維護者提交，**Then** 提交被阻止，訊息列出該檔案並說明如何處理。
2. **Given** 暫存了白名單內的檔案，**When** 維護者提交，**Then** 該檔案不會因範圍檢查被阻止，仍需通過內容掃描。
3. **Given** 白名單初次建立，**When** 檢查 repo 目前已追蹤的檔案，**Then** 所有已追蹤檔案都落在白名單內。
4. **Given** 刪除一個白名單外的已追蹤檔案，**When** 維護者提交，**Then** 刪除可以完成，不會被範圍檢查阻止。

---

### User Story 3 - 公開前檢查完整歷史與全部檔案 (Priority: P2)

維護者在公開 repo 前，能隨時對目前全部已追蹤檔案與完整 git 歷史（含作者資訊與 commit 訊息）執行同一套檢查，並得到明確的通過或不通過結果。

**Why this priority**: commit 防護只保護啟用後的新提交，也可能在未啟用的機器上被略過。公開前需要一次完整確認，但它建立在 P1 的檢查規則之上。

**Independent Test**: 在歷史中刻意留下一個已被後續 commit 刪除的假憑證，執行檢查，確認會回報其所在的 commit 與檔案。

**Acceptance Scenarios**:

1. **Given** 歷史中曾有假憑證但目前的檔案已移除，**When** 執行完整檢查，**Then** 回報不通過，並指出 commit 與檔案。
2. **Given** 舊 commit 的作者 email 不是公開安全的地址，**When** 執行完整檢查，**Then** 回報不通過。
3. **Given** 歷史與檔案都沒有違規，**When** 執行完整檢查，**Then** 回報通過。

---

### User Story 4 - 檢視現有設定並判斷可否共用 (Priority: P2)

維護者要把現有的 `~/.claude/settings.json` 納管前，能取得一份逐項分類報告，知道哪些項目可以共用、哪些含機密、哪些屬於機器專屬、哪些需要自己判斷。檢視過程不會修改原始設定。

**Why this priority**: 現有設定很大，人工逐行判斷容易遺漏，但在白名單與掃描就緒前不應納管任何設定，所以排在 P1 之後。

**Independent Test**: 準備一份含假 token、絕對路徑與一般偏好的設定檔，執行檢視，確認分類正確、原始檔完全未變，報告中也沒有假 token 的值。

**Acceptance Scenarios**:

1. **Given** 設定含 token 格式的值，**When** 執行檢視，**Then** 該項目標為「含機密」，報告只顯示鍵名與類型，不顯示值。
2. **Given** 設定含個人絕對路徑，**When** 執行檢視，**Then** 該項目標為「機器專屬」。
3. **Given** 設定含一般偏好，**When** 執行檢視，**Then** 該項目標為「可共用」。
4. **Given** 工具無法確定某項目的性質，**When** 執行檢視，**Then** 該項目標為「待判斷」，不會預設為可共用。
5. **Given** 檢視完成，**When** 比對原始設定檔，**Then** 內容完全未變，repo 內也沒有新增報告檔案。

---

### Edge Cases

- **檢查本身失敗**（例如無法讀取內容或白名單遺失）：提交 MUST 被阻止並說明原因，不得視為通過。
- **誤判**：維護者可為特定位置記錄誤判例外，例外必須寫明理由，且不得包含機密原文。
- **防護未啟用**：新 clone 預設沒有啟用 commit 防護，維護者要能查出目前機器是否已啟用。
- **略過防護**：提交時可用 git 內建選項略過本機檢查，這由 User Story 3 的完整檢查補上。
- **二進位檔案**：無法掃描內容的二進位檔案預設阻止，除非其路徑被明確列為允許。
- **重新命名**：把檔案改名到白名單外時，視同新增白名單外的檔案。
- **路徑格式差異**：同一條白名單規則在 Windows 與 Linux 的判斷結果 MUST 相同，不受路徑分隔符號與換行格式影響。
- **公開安全的 email**：GitHub noreply 地址與 commit 署名所用的工具 noreply 地址不算違規；測試資料中的假 email 使用保留網域。
- **防護自身的測試資料**：測試用的假機密不得是真實憑證，也 MUST 能通過防護或被記錄為例外。
- **個人專屬識別資訊**：維護者的真實姓名、私人主機名稱這類無法靠格式辨識的資訊，透過 repo 外的本機清單比對。

## Requirements *(mandatory)*

### Functional Requirements

**Commit 防護**

- **FR-001**: 系統 MUST 在每次 commit 完成前自動檢查待提交內容，發現違規時阻止提交。
- **FR-002**: 系統 MUST 偵測憑證與 token、email、Windows 與 Linux 的個人路徑。
- **FR-003**: 系統 MUST 檢查作者與提交者的 email，以及 commit 訊息。
- **FR-004**: 系統 MUST 依暫存區內容判斷，而不是工作區內容。
- **FR-005**: 違規訊息 MUST 包含位置、類型與修正方向，且 MUST NOT 顯示機密的完整值。
- **FR-006**: 檢查無法完成時，系統 MUST 阻止提交。

**白名單**

- **FR-007**: 系統 MUST 用 repo 內的一份白名單定義可納管路徑，未列入者一律不可提交。
- **FR-008**: 白名單檢查 MUST 不受一般忽略規則影響，被強制加入暫存區的檔案同樣受檢。
- **FR-009**: 從 repo 移除檔案的提交 MUST NOT 被白名單阻止。
- **FR-010**: 初始白名單 MUST 沿用 002 建立的 `.repo-allowlist`，並 MUST NOT 涵蓋整個 `~/.claude/`。本功能的防護 MUST 取代 `tools/check_allowlist.py` 與其 pre-commit hook。`tests/fixtures/sample-project/` 的假憑證 MUST 記錄為誤判例外。

**誤判與本機清單**

- **FR-011**: 維護者 MUST 能記錄誤判例外，每筆例外 MUST 指明位置並寫明理由。
- **FR-012**: 例外 MUST 只適用於指定位置，MUST NOT 關閉整個類型的偵測。
- **FR-013**: 維護者 MUST 能維護一份存放在 repo 外的本機個人識別清單，系統 MUST 據此比對，且比對結果與清單內容 MUST NOT 寫入 repo。

**完整檢查**

- **FR-014**: 維護者 MUST 能隨時對全部已追蹤檔案與完整 git 歷史（含作者資訊與 commit 訊息）執行檢查。
- **FR-015**: 完整檢查 MUST 給出明確的通過或不通過結果，並指出違規的 commit 與檔案。

**設定檢視**

- **FR-016**: 維護者 MUST 能檢視 `~/.claude/settings.json`，並得到逐項分類：可共用、含機密、機器專屬、待判斷。
- **FR-017**: 檢視 MUST NOT 修改原始設定，MUST NOT 在 repo 內產生檔案，報告 MUST NOT 顯示被判定為機密的值。
- **FR-018**: 無法確定性質的項目 MUST 標為「待判斷」。

**平台與啟用**

- **FR-019**: 上述所有功能 MUST 在 Windows 與 Linux 上行為一致。
- **FR-020**: 維護者 MUST 能在新 clone 上以一個步驟啟用 commit 防護，重複執行結果相同。
- **FR-021**: 維護者 MUST 能查出目前機器的 commit 防護是否已啟用。
- **FR-022**: 每個功能 MUST 附自動化驗證，涵蓋應阻止與應放行的情況。

### Key Entities

- **白名單**: 可納管路徑的清單，存放於 repo，是判斷檔案能否入庫的唯一依據。
- **違規**: 一筆檢查結果，包含位置（檔案與行號，或 commit）、類型與修正方向，不含機密原文。
- **誤判例外**: 對特定位置的豁免紀錄，包含位置與理由，存放於 repo。
- **本機識別清單**: 維護者的個人識別資訊，只存放在各機器本機，不入庫。
- **設定項目分類**: 設定中每個項目的判定結果，分為可共用、含機密、機器專屬、待判斷四類。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 驗收樣本中涵蓋的每一種機密與個資類型，100% 在 commit 前被阻止，Windows 與 Linux 結果相同。
- **SC-002**: 白名單外的檔案 100% 無法透過已啟用防護的 commit 進入 repo。
- **SC-003**: 正常提交的等待時間增加不超過 2 秒（以單次提交 50 個檔案以內為準）。
- **SC-004**: 維護者看到違規訊息後，不需查閱其他文件就能知道該修改哪個位置。
- **SC-005**: 所有違規訊息與設定檢視報告中，出現驗收樣本機密完整值的次數為 0。
- **SC-006**: 維護者能在 1 分鐘內於新 clone 上啟用防護並確認狀態。
- **SC-007**: 公開 repo 前，完整檢查對目前的歷史與檔案回報通過。
- **SC-008**: 現有 `settings.json` 的每個頂層項目都得到分類，沒有遺漏。

## Assumptions

- **使用者**：只有一位維護者，使用自己的 Windows 與 Linux 機器；macOS 不在範圍內。
- **commit 防護的限制**：本機檢查可以被略過，也不會隨 clone 自動啟用，因此以完整檢查作為公開前的最終確認。
- **遠端防護不在範圍內**：目前沒有 remote，伺服器端或 CI 檢查留待設定 remote 時另外處理。
- **偵測範圍**：格式偵測無法保證找出所有機密，白名單與本機識別清單用來降低這個風險；SC-001 以驗收樣本為準。
- **不重寫歷史**：完整檢查只回報問題，不會自動修改 git 歷史；若發現真實機密，依憲章原則 I 視為已外洩並更換。
- **不自動納管設定**：設定檢視只產生分類報告，實際納管設定與安裝流程屬於後續功能。
- **Spec Kit 檔案**：`.specify/` 與 `.claude/skills/speckit-*` 視為 repo 內容，同樣受白名單與掃描保護。
